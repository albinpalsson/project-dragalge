# Database Module Specification

## Overview

A lightweight, offline-first in-memory database engine with binary row storage.
The engine exposes a `DbClient` interface (from `@pokedb2/query-builder`) so app code
uses the query builder for all data access — no direct CRUD calls on the DB.

```ts
const engine = new DB(new FilePersistencePlugin('pokedb.bin'))
engine.createTable('pokemon', schema)

const db = createDb<MyDB>(engine) // engine satisfies DbClient
const rows = await db.selectFrom('pokemon').where('caught', '=', false).selectAll().execute()
```

Swapping the storage backend means replacing `DB` with a different `DbClient` implementation.
The query builder and all app code are unaffected.

---

## DbClient Integration

The `DB` class implements `DbClient` from `@pokedb2/query-builder`:

```typescript
import type { DbClient } from '@pokedb2/query-builder'

class DB implements DbClient {
  execute(sql: string, parameters: readonly unknown[]): Promise<unknown[]>
}
```

`execute()` runs a parameterised SQL string and returns the result rows as plain objects.
All SQL is generated by the query builder — app code never writes raw SQL directly.

## Requirements (In-Scope)

### Operations Supported

#### Raw SQL Interface (Primary)
- `execute(sql, params?)`: Execute raw SQL with parameterized values
  - Example: `db.execute("SELECT * FROM pokemon WHERE id = ?", [1])`
  - Example: `db.execute("INSERT INTO pokemon (name, level) VALUES (?, ?)", ["Pikachu", 5])`
  - Example: `db.execute("UPDATE pokemon SET caught = 1 WHERE id = ?", [1])`
  - Returns: Array of objects for SELECT, `{ changes: number }` for INSERT/UPDATE/DELETE

#### Prepared Statements (Efficiency)
- `prepare(sql)`: Create prepared statement for repeated execution
  - `stmt.bind(params)`: Bind parameters once
  - `stmt.all()`: Execute and get all rows
  - `stmt.get()`: Execute and get first row
  - `stmt.run()`: Execute write operation

#### High-Level Convenience Methods (for app code)
- `insert(table, row)`: Helper (uses raw SQL internally)
- `select(table, where?)`: Helper (uses raw SQL internally)
- `update(table, set, where)`: Helper (uses raw SQL internally)
- `delete(table, where)`: Helper (uses raw SQL internally)

### WHERE Clause & SQL Support
- **Parameterized queries**: `?` placeholders for safe value binding
  - Example: `SELECT * FROM pokemon WHERE location = ? AND caught = ?` with params `['Mt. Moon', true]`
- **Equality predicates only**: `column = ?`
- **AND logic only** (no OR for v1)
- **Minimal JOIN support**: single `INNER JOIN` for critical relational lookups
- **Basic SQL operations**: SELECT, INSERT, UPDATE, DELETE, CREATE TABLE
- Examples:
  ```sql
  SELECT * FROM pokemon WHERE location = ? AND caught = ?
  UPDATE encounters SET visited = 1 WHERE location = ?
  INSERT INTO caught (pokemon_id, caught_at) VALUES (?, ?)
  SELECT * FROM encounters e INNER JOIN pokemon p ON e.pokemon_id = p.id WHERE e.game_id = ?
  ```

### JOIN Scope (V1)
- Support exactly one `INNER JOIN` between two tables in a single query.
- Support equality join predicates only: `left.col = right.col`.
- No multi-join chains.
- No `LEFT/RIGHT/FULL` joins.
- No join condition expressions beyond simple equality.
- Correctness over performance: nested-loop join implementation is acceptable.

### Application-Level Data Integrity Protocol (V1)

Engine-level constraints are intentionally minimal for v1.

- `PRIMARY KEY`, `UNIQUE`, and `FOREIGN KEY` may be declared in schema metadata for documentation only.
- The engine does not enforce those constraints in v1.
- The application layer is responsible for:
  - ID generation and stable identity
  - de-duplication checks before insert where needed
  - referential consistency checks in critical flows

### Parameterized Query Safety
- All values use `?` positional placeholders, matching what `@pokedb2/query-builder` produces
- Values passed separately in `parameters` array
- Protects against SQL injection

### Persistence
- `save()`: concatenate raw table buffers with a directory header and hand to `StoragePlugin`
- `load()`: read blob from `StoragePlugin`, slice into table buffers, rebuild `freeList`
- `onChange`: callback fired after any write (for auto-save wiring)

### StoragePlugin Goal
- One opaque blob in, one opaque blob out — the plugin knows nothing about table layout.
- Different runtimes provide different plugins without changing DB behaviour.

Examples:
- Browser app: `LocalStoragePersistencePlugin`
- Node / desktop: `FilePersistencePlugin`
- Tests: in-memory stub `{ read: () => null, write: () => {} }`

### Storage Constraints (V1)

**Key design decision: the in-memory `ArrayBuffer` per table IS the storage format.**
There is no row serialization or deserialization. `save()` concatenates raw table buffers
with a tiny directory header; `load()` slices the blob and assigns each slice directly as
the table’s live buffer. Rows are never parsed during load.

- **Column types**: `int32`, `boolean`, `timestamp` (int64, ms since epoch), `char(n)` (inline, zero-padded)
- **No `text` columns**: all strings use `char(n)` with a declared max byte length
- **No `float64`**: not needed for Pokémon game data
- **No nulls**: every column must have a value
- **Schema stays in code**: column offsets and row size are registered via `createTable()` at startup — not stored in the buffer
- **Schema fixed after creation**: no `ALTER TABLE` in v1
- **Tombstone deletes**: deleted slots are marked, not removed, and reused by the next insert
- **Compaction is explicit only**: run via `compact(table?)` when needed; never triggered automatically

Recommended `char(n)` lengths:
- short names / status values: `char(32)`
- route / location names: `char(48)`

### Error Handling
- Throw on schema mismatch (INSERT with wrong columns)
- Throw on invalid WHERE syntax
- Graceful handling of missing columns in WHERE clauses
- Throw when a `char(n)` value exceeds its allocated byte length

## Design & Architecture

### Core Data Structure

```typescript
type ColumnType = 'int32' | 'boolean' | 'timestamp' | 'char'

interface ColumnDefinition {
  name: string
  type: ColumnType
  length?: number  // required for char(n), in bytes
  offset: number   // byte offset within the row payload (after the 1-byte status)
}

interface TableSchema {
  columns: ColumnDefinition[]
  rowSize: number   // 1 status byte + sum of column byte widths
  primaryKey?: string  // documentation only in v1
}

// Runtime table — the buffer itself stores header + row slots
interface TableStorage {
  name: string
  schema: TableSchema
  buffer: ArrayBuffer   // layout: [header 12 bytes][row slots...]
  view: DataView
  freeList: number[]    // rebuilt from tombstone scan on load; not persisted
}

// buffer header layout (bytes 0-11):
//   rowCount    u32 @ 0
//   rowCapacity u32 @ 4
//   deletedCount u32 @ 8
// row slots start at byte 12
```

### Persistence Boundary

The table `ArrayBuffer` is the storage format — no row-level parse step exists.

`save()` writes a single blob:
```
[magic: u32][tableCount: u32]
  per table: [nameLen: u8][name bytes: nameLen][offset: u32][byteLen: u32]
[table0 buffer bytes]
[table1 buffer bytes]
...
```

`load()` reads the blob, parses the tiny directory (a handful of u32/u8 values), slices the
buffer for each registered table, and assigns the slice directly as the live table buffer.
Afterward a single O(n) tombstone scan rebuilds the `freeList` for each table. No row decoding
happens during load.

The persistence plugin stores and retrieves one opaque `Uint8Array` blob and knows nothing
about table internals.

### Binary Row Layout

Each table is a contiguous `ArrayBuffer` with a fixed 12-byte header followed by fixed-size row slots.

```text
buffer := [rowCount: u32][rowCapacity: u32][deletedCount: u32][slot 0][slot 1]...

slot   := [status: u8][column bytes...]
```

Row status values:
- `0`: never used / free
- `1`: active
- `2`: deleted (tombstone)

Column encodings:
- `int32`: 4 bytes, little-endian
- `boolean`: 1 byte (`0` or `1`)
- `timestamp`: 8 bytes, little-endian int64 (Unix ms)
- `char(n)`: exactly `n` bytes, zero-padded on write, trailing zero bytes trimmed on read

### API Signatures

```typescript
import type { DbClient } from '@pokedb2/query-builder'

interface StoragePlugin {
  read(): Promise<Uint8Array | null> | Uint8Array | null
  write(blob: Uint8Array): Promise<void> | void
}
```

#### DB Class

```typescript
class DB implements DbClient {
  constructor(storage?: StoragePlugin)

  // DbClient — called by query builder builders
  execute(sql: string, parameters: readonly unknown[]): Promise<unknown[]>

  // Schema management
  createTable(name: string, schema: Omit<TableSchema, 'rowSize'>): void

  // Persistence
  load(): Promise<boolean>   // true if a blob was found and loaded
  save(): Promise<void>
  setStorage(plugin: StoragePlugin | undefined): void

  // Events
  onChange(callback: (table: string) => void): void

  // Explicit compaction (never automatic)
  compact(table?: string): void
}
```

### Implementation Strategy

#### V1: In-Memory SQL Engine

```
App code
  → createDb<DB>(engine)       // @pokedb2/query-builder
  → .selectFrom('pokemon')...compile()  // query builder produces { sql, parameters }
  → engine.execute(sql, parameters)     // DB.execute() runs the SQL
  → binary row scan + decode            // internal engine
  → plain object array                  // returned to query builder
```

SQL arrives pre-built from the query builder. The engine only needs to parse and run the
specific SQL patterns that `@pokedb2/query-builder` produces — no general SQL parser needed.

1. **Table Storage**: `Map<string, TableStorage>` — each entry wraps one `ArrayBuffer`
2. **SQL Parsing**: minimal tokenizer for the 5 patterns the query builder produces
   - Extract table, optional JOIN, WHERE conditions, column/value lists
   - Bind `?` placeholders to the `parameters` array
3. **WHERE evaluation**: equality + AND only; short-circuit on first mismatch
4. **Change Tracking**: emit `onChange(table)` after each write
5. **Insertion**: reuse a slot from `freeList` if available; otherwise grow the buffer
6. **Persistence**: `save()` copies raw buffers into a blob with a tiny directory header;
   `load()` slices the blob and assigns slices to table buffers, then rebuilds `freeList`
   from a tombstone scan

#### Controlled Compaction Strategy

Compaction is explicit only — never triggered automatically.

Algorithm:
1. Allocate a new buffer sized for active rows only (12-byte header + active row slots).
2. Scan old slots; copy only active rows into the new buffer sequentially.
3. Update the header (`rowCount`, `rowCapacity`, `deletedCount = 0`).
4. Clear `freeList`.
5. Swap the new buffer into `TableStorage`.

Simple because: fixed-width slots, no text section, no secondary structures.

#### JOIN Execution Strategy (V1)

- Implement `INNER JOIN` using a straightforward nested-loop strategy.
- Evaluate join predicate as strict equality after decoding join columns.
- Apply WHERE filtering after row pairing.
- This is intentionally not index-optimized; correctness is the priority.

#### Persistence Flow

```text
save():
  for each table: copy buffer bytes into blob
  prepend directory header (magic + table offsets)
  StoragePlugin.write(blob)

load():
  StoragePlugin.read() → blob
  parse directory header (u32/u8 values only)
  for each registered table: slice blob → assign as table.buffer
  for each table: scan tombstones → rebuild freeList   (O(n), no row decode)
```

#### Why Binary-First Runtime Is Reasonable Here

This is only practical because v1 deliberately constrains the model:
- fixed-width row slots
- fixed-length `char(n)` plus bounded `text` support for strings only
- no nulls
- no schema mutations
- full scans instead of indexes

Those constraints remove most of the complexity that usually makes binary-first engines expensive to build.

### Example Usage

#### Setup

```typescript
import { createDb } from '@pokedb2/query-builder'
import { DB } from '@pokedb2/db'
import type { MyDB } from './schema'

const engine = new DB(new FilePersistencePlugin('pokedb.bin'))
await engine.load()

engine.createTable('pokemon', {
  columns: [
    { name: 'id',       type: 'int32',   offset: 1  },
    { name: 'name',     type: 'char',    length: 32, offset: 5  },
    { name: 'location', type: 'char',    length: 48, offset: 37 },
    { name: 'caught',   type: 'boolean', offset: 85 },
    { name: 'level',    type: 'int32',   offset: 86 },
  ],
  primaryKey: 'id',
})

const db = createDb<MyDB>(engine)
```

Recommended `char(n)` lengths:
- short names / status values: `char(32)`
- route / location names: `char(48)`

#### Queries (via query builder)

```typescript
// SELECT
const rows = await db.selectFrom('pokemon')
  .where('location', '=', 'Route 1')
  .where('caught', '=', false)
  .selectAll()
  .execute()

// INSERT
await db.insertInto('pokemon')
  .values({ id: 1, name: 'Pikachu', location: 'Viridian Forest', caught: false, level: 5 })
  .execute()

// UPDATE
await db.updateTable('pokemon').set({ caught: true }).where('id', '=', 1).execute()

// DELETE
await db.deleteFrom('pokemon').where('id', '=', 1).execute()

// Compile only (no execution)
const { sql, parameters } = db.selectFrom('pokemon').selectAll().compile()
```

#### Persistence

```typescript
// Auto-save after mutations
engine.onChange(async () => { await engine.save() })

// Load into a fresh instance
const engine2 = new DB(new FilePersistencePlugin('pokedb.bin'))
await engine2.load() // slices blob directly into table buffers; no row parsing
```

#### Persistence Plugins

```typescript
class LocalStoragePersistencePlugin implements StoragePlugin {
  constructor(private key: string) {}
  read(): Uint8Array | null {
    const encoded = localStorage.getItem(this.key)
    return encoded ? decodeBase64ToBytes(encoded) : null
  }
  write(blob: Uint8Array): void {
    localStorage.setItem(this.key, encodeBytesToBase64(blob))
  }
}

class FilePersistencePlugin implements StoragePlugin {
  constructor(private path: string) {}
  async read(): Promise<Uint8Array | null> { return readFileAsBytes(this.path) }
  async write(blob: Uint8Array): Promise<void> { await writeFileBytes(this.path, blob) }
}
```

## Verification

### Unit Tests
- [ ] `execute()`: INSERT, SELECT, UPDATE, DELETE with `?` parameters produce correct results
- [ ] SELECT: equality WHERE + AND chain filters rows correctly
- [ ] SELECT: single INNER JOIN equality predicate returns merged rows; non-matching rows excluded
- [ ] SELECT: unsupported SQL (OR, IN, LIKE, ORDER BY, outer joins) throws
- [ ] INSERT: schema mismatch throws; `char(n)` overflow throws
- [ ] Binary encoding: int32, boolean, timestamp, char(n) round-trip via DataView
- [ ] Tombstones: deleted rows skipped by scans; slots reused on next insert
- [ ] Compaction: live rows preserved, deleted rows removed, freeList cleared, header updated
- [ ] Persistence: `save()` + `load()` preserves all rows without row parsing
- [ ] `load()` is a no-op when plugin returns null
- [ ] `freeList` correctly rebuilt from tombstone scan after `load()`
- [ ] `onChange`: fired after INSERT / UPDATE / DELETE, not after SELECT

### Integration Tests
- Load seed data (Pokémon table) → query by location → verify results
- Update encounter status → export → import → verify persistence
- Multiple queries in sequence without cross-contamination

### Performance Targets
- Insert 1000 rows: <10ms
- Select with WHERE from 1000 rows: <5ms
- `save()` + `load()` round-trip for 1000 rows: <5ms
